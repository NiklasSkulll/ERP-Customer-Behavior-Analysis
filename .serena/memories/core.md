# Project source map and invariants
- Bachelor's thesis on retrospective detection, typing and evidence-based description of purchasing changes at a B2B wholesaler; research repository, not a deployed service.
- Authority: docs/project/bachelor_thesis_project_plan.md defines scope, objectives, eligibility principles and evaluation commitments. docs/framework/fuucce_framework.md operationalises six FUUCCE phases. docs/project/data_description.md defines raw/interim/processed schemas and calculation contracts; implementation does not override these documents.
- Current scope: 24 months of sales-order header information; ORDERCOUNT, TOTALORDERNETVALUE and AVGORDERNETVALUE. Product, assortment, quantity, price-condition and discount analyses are outside scope. Industry supplies context, not an eligibility filter. Recorded nominal net amounts are not realised revenue.
- Raw basis: 001_order_header_pos_data.csv, 002_customer_master_data.csv, 003_order_sddocumentreason_mapping.csv, 004_customer_industry_mapping.csv. Item rows repeat headers; retain each order amount once. Interim: one enriched row per SALESORDER. Processed: monthly profiles keyed by CUSTOMER_ID, PERIODSTART, TRANSACTIONCURRENCY. Keep EUR/GBP monetary histories separate.
- FUUCCE: Familiarise and assess → Use data and prepare profiles → Uncover and characterise changes → Construct taxonomy → Classify and explain → Evaluate and discuss. Main approach compares time windows of monthly profiles; classify events, allow compatible types/ambiguity, retain evidence. The three measures are mathematically dependent.
- Separate development from final evaluation; fix preparation/detection/taxonomy/description rules before final evaluation. Controlled scenarios, held-out real cases and sensitivity analyses support distinct claims. Without a user study, description correctness/completeness/traceability do not demonstrate usefulness or comprehension.
- docs/project/notebook_template.md defines eight sections for one notebook per phase, including configuration discovery. docs/project/report_template.md defines reports; its referenced setup/create_markdown_report.py is absent. Do not infer an implementation from a template claim.
- Existing src/notebooks/001_f_phase_1.ipynb contains assessment code but still uses eight legacy *_eg.parquet inputs, product/price features and old names such as TOTALORDERVALUE/CUSTOMERID. Align it with current scope/schema/template before treating it as the current workflow. Implementation availability is not empirical completion.
- Utilities live in setup/. Markdown is authoritative; docs/docsite/ is generated, including potentially stale copies of memories. Literature and remaining historical prompts live in docs/literature/ and docs/prompts/.
- Never inspect/search/execute against/modify data/data-prd/, src/.notebooks/, outputs/.exports/, or production-derived content elsewhere. A data-example directory does not establish synthetic provenance.
- setup/create_example_dataset.py is a dataset randomization utility: it transforms an input dataset into CSV copies with randomized IDs and amounts while retaining rows and relationships. Outputs are input-derived, not fully synthetic or guaranteed anonymous. Verify this utility only with invented fixtures.
- Public source notebooks use explicit example configuration; the user maintains private production copies. src/raw-notebooks/ mirrors are read-only: no agent edits, deletion, regeneration or synchronization.
- AGENTS.md is the default repository workflow; HANDOVER.md holds session history and BACKLOG.md task status. Explicit session instructions override that workflow. Do not infer task completion from a memory.
- Environment/config and notebook imports: `mem:tech_stack`. Data, utility and docsite contracts: `mem:conventions`. Entry points and traversal hazards: `mem:suggested_commands`. Verification/closeout: `mem:task_completion`. Memory graph policy: `mem:memory_maintenance`.
